# Security — 5 findings

Both critical findings sit in the same place: a control that was built correctly, next to an older path that quietly bypasses it. The hardening work is real — it just didn't close the back door behind it.

---

### SEC-1 · CRITICAL — The Patient Access Code enumeration oracle is still open, and the test suite asserts it as correct

**What I found**

`firestore.rules:425` still carries `allow get: if true` on `/hospitalIds/{id}`. Because the document ID *is* the access code (`CRMC-YYYY-NNNNN`), anyone on the internet can ask Firestore's REST API directly whether a given code exists and whether its `status` is `available` — no auth, no throttle, no log, no browser.

```
GET https://firestore.googleapis.com/v1/projects/<id>/databases/
    (default)/documents/hospitalIds/CRMC-2026-00001?key=<public web key>
```

That is precisely the vector `verifyAccessCode` was built to close. Its dual-layer throttle (10/hr per uid, 60/hr per IP) is careful work — and completely bypassed, because nothing forces an attacker through the callable at all. The function's own comment names the gap: *"Server-side reads bypass the parent doc's public-get exposure."*

Two things make it worse:

- `Register.jsx:372` keeps an explicit **fallback that reads `hospitalIds/{code}` directly** whenever the callable errors — so the bypass is a supported code path, not just a rules leftover.
- `tests/rules/hospitalIds.rules.test.js:53` asserts *"allows an unauthenticated client to GET the parent doc"* as expected behaviour. The regression guard at line 85 protects only the patient *name* in `privateInfo`. The PII half of the leak was closed; the availability half was locked in green.

The code space is 100,000 values per year. A script walks it in minutes, harvests every unclaimed code, and registers as a patient with someone else's identity gate.

**Fix**

- **Minimum:** flip `allow get: if true` → `if isAuth()`. The claim transaction does `tx.get(hidRef)` after the Auth account exists, so registration keeps working. Then delete the `Register.jsx` fallback and let the callable fail closed.
- **Proper:** move the whole claim into a Cloud Function using the Admin SDK, then lock the collection to `allow get, list: if isAdmin()`. The client never touches `hospitalIds` again and the throttle becomes unavoidable.
- **Either way:** rewrite that rules test to assert *denial*. A test that certifies the hole is worse than no test.

### SEC-2 · CRITICAL — `/api/send-email` is an unauthenticated open relay sending as CRMC

**What I found**

The Vercel route accepts `POST` from anyone, with `Access-Control-Allow-Origin: '*'` and no token check. The caller supplies `to`, `subject`, `text` and `html` verbatim; the route sends them over authenticated Gmail SMTP from the official MAPA/CRMC address.

*`api/send-email.js:32–89` · called from `src/utils/notifications.js:88`*

Anyone can therefore send SPF/DKIM-valid mail that genuinely originates from CRMC, to any address, with any body. Pair it with SEC-1 and you have a full phishing chain aimed at exactly the population this system exists to protect: enumerate live access codes, then mail patients from the real CRMC sender asking them to "confirm" one.

There's a second, quieter failure mode. The only volume limit is Gmail's 500/day App Password cap. Five hundred junk POSTs exhaust it, and then *no patient receives any notification email for the rest of the day* — a one-request denial of service against the whole notification channel.

The file's header comment already flags this as a pre-production task. It is worth treating as shipped-and-live rather than deferred, because the pilot deployment is live.

**Fix** — three changes, roughly twenty lines:

- Require a Firebase ID token in `Authorization`; verify it with `firebase-admin` and reject anything unsigned.
- Replace `'*'` with the deployment origin.
- Stop trusting `to`. Resolve the recipient server-side from the verified uid (or from the `notifications/{uid}` doc being announced) so an authenticated patient still can't relay mail to arbitrary addresses.

The durable version is a Firestore-triggered Cloud Function on the notification write — you already run Functions in `asia-southeast1`, so the client never sees a mail endpoint at all.

### SEC-3 · HIGH — The `agencies` collection is world-readable, budget figures included

**What I found**

`firestore.rules:352` — `allow read: if true` on `/agencies/{id}`, with no auth gate at all. Those documents carry `budget.allocated`, `budget.committed`, `budget.disbursed`, `slots`, `fundSource`, contact details and signatory names for PCSO, DSWD, AMBaG and every other partner.

Partner agencies' internal allocation and burn-down figures becoming publicly scrapeable is a governance problem before it's a technical one — it's the kind of thing a partner MOA would have something to say about, and the kind of question a panel enjoys asking.

Nothing needs it. `LiveDataContext.jsx:153` subscribes only when `user?.uid` is set, and its own comment assumes signed-in access.

**Fix**

`allow read: if isAuth()`. One character class of change, no client code affected.

If a future public "browse programs" page needs unauthenticated agency data, split the public fields (name, description, requirements) into a separate `agencyPublic` collection rather than reopening this one.

### SEC-4 · MEDIUM — No security response headers on the deployment

**What I found**

`vercel.json` sets caching and content-type headers but no `Content-Security-Policy`, `X-Frame-Options` / `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` or `Strict-Transport-Security`.

For a system handling medical and financial-hardship records this is the first thing an external assessor greps for, and clickjacking on the admin surfaces is a live risk without `frame-ancestors`. It's also the cheapest defensible win in this entire document.

**Fix**

Add a headers block for `/(.*)`. Start with `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, `frame-ancestors 'none'` and an HSTS max-age.

Add CSP last and in `Content-Security-Policy-Report-Only` first — Firebase, Google Fonts and the PWA worker all need explicit `connect-src` / `font-src` entries, and a strict policy shipped blind will break auth.

---

### SEC-5 · LOW — Client-side verify throttle is decorative

**What I found**

`Register.jsx` keeps a `countRecentVerifyAttempts` guard alongside the server throttle. It's fine as a UX affordance — it stops an honest user hammering the button — but it lives entirely in the client and is not a security control.

Flagging it only because the surrounding comments treat it as part of the defense ("the client-side throttle is still in place" as justification for the SEC-1 fallback). If that framing reaches the manuscript, it's an easy thing for a panel to pull on.

**Fix**

Keep the code, change the comment. Describe it as rate-limiting the *UI*, and make sure the thesis' security chapter counts server-side layers only.

# Correctness — 2 findings

Enabling the React Hooks lint rules — installed, registered, but never switched on — surfaced these immediately. Nothing else in 36,895 lines turned up as a hard defect, which is a genuinely good result.

---

### BUG-1 · HIGH — Conditional `useMemo` in ExportPreview will white-screen the admin

**What I found**

`ExportPreview.jsx:318` returns early when `!config` (the unknown-export-type 404 guard). `docIndexMap`'s `useMemo` sits at line 335, *after* that return.

*`react-hooks/rules-of-hooks` — `src/pages/admin/ExportPreview.jsx:336`*

The route is `/admin/export/:type`, so changing `:type` re-renders the same component instance rather than remounting it. Walk from a valid export type to an invalid one — a stale bookmark, a typo, a renamed export — and the hook count drops between renders. React throws *"Rendered fewer hooks than expected"*, the ErrorBoundary catches it, and the admin gets a blank recovery screen instead of the intended "Unknown export type" message.

Worth fixing before defense specifically because it's reachable by mistyping a URL during a live demo.

**Fix**

Move the `useMemo` above the `if (!config)` return. It only depends on `docs`, so nothing else has to move.

While you're there: `selectedCount` is declared at line 333 but used at line 312 in `printSelected` — legal via closure, but confusing to read. Hoist both.

---

### BUG-2 · LOW — Five conditional `useState` calls in the Seed page

**What I found**

`Seed.jsx:70–74` calls `useState` five times after a conditional return. Low severity only because the route is gated behind `VITE_ENABLE_SEED === 'true'` and shouldn't exist in production.

It matters for a different reason: `docs/handoff-2026-06-29.md` tells the operator to reseed demo data from this page during defense rehearsal. If the flag is on for a demo, this is a page that can crash mid-demo.

**Fix**

Hoist the five `useState` calls above the guard. Then confirm `VITE_ENABLE_SEED` is unset in the Vercel production environment — the route registration in `App.jsx:102` is build-time, so an unset flag removes it entirely.

# Accessibility — 4 findings

This is the weakest area, and the one with the highest ratio of impact to effort. A government-adjacent health service for indigent patients — many elderly, many on cheap phones in daylight — has a strong claim to WCAG 2.1 AA, and that claim is currently not defensible. The good news: two of the four are close to one-file fixes.

---

### A11Y-1 · HIGH — Almost no form control in the app is associated with its label

**What I found**

Across `src/`: **142 `<label>` elements, 4 with `htmlFor`. 163 `<input>` elements, zero with an `id`.** The labels are siblings, not wrappers, so there's no implicit association either.

Consequences: screen readers announce "edit text, blank" with no field name; tapping a label doesn't focus its input (a real cost on a phone); and voice control can't address fields by name. axe confirms it live — `select-name` fires as *critical* on the name-suffix dropdown at `Register.jsx:596`, on the registration form, in the flow every single patient must complete.

The leverage point is one file. `components/ui/Field.jsx` — the shared field primitive extracted precisely so forms would share one implementation — renders the label as a sibling of `{children}` with no wiring. Every form built on it inherits the defect, and every one of them is fixed by fixing it.

**Fix**

Rewrite `Field.jsx` with `useId()`, put the id on the label's `htmlFor`, and pass it down via `cloneElement` (or a render prop, if you'd rather be explicit):

```jsx
const id = useId()
<label htmlFor={id}>{label}</label>
{cloneElement(children, { id,
  'aria-describedby': hint ? `${id}-hint` : undefined })}
```

Then sweep the hand-rolled forms — `Login`, `Register`, `Accounts`, `AddAgency`, `ProfileModals` — onto `Field` or onto the same id pattern. `AddressPicker.jsx` already got this treatment; it's the model to copy.

---

### A11Y-2 · HIGH — 739 uses of a grey that fails AA at 2.53:1, including instructional copy

**What I found**

`text-gray-400` is `#9ca3af`: **2.53:1 on white, 2.42:1 on `bg-gray-50`**. WCAG AA requires 4.5:1 for body text and 3:1 for large text and UI components — this clears none of them. It appears 739 times. `text-gray-300` (1.47:1) adds another 63, mostly empty-state icons.

axe flags it as *serious* on every public route. The specific hits are the worst possible ones — `Register.jsx`: *"Enter your name and contact details as they appear on your official ID."* The single most important instruction on the registration form, rendered at half the required contrast. Also caught: `text-white/70` on brand green at 3.3:1 in the access-code helper card, and an actionable button at `TrackStatus.jsx:894`.

This is a design-token problem, not 739 individual bugs — which is why it's cheap to fix.

**Fix**

Sweep `text-gray-400` → `text-gray-500` (`#6b7280`, 4.83:1 — passes) for anything that is text, and `text-gray-300` → `text-gray-400` for decorative icons. A scripted replace plus a visual pass gets you most of the way in an afternoon.

Then define `muted` and `subtle` as semantic colors in `tailwind.config.js` so the next contributor can't reintroduce it. Bump `text-white/70` to `/85`.

Worth doing before defense: "WCAG 2.1 AA verified with axe-core" is a strong sentence for the manuscript, and it's currently within reach.

---

### A11Y-3 · MEDIUM — Icon-only controls with no accessible name

**What I found**

axe reports `button-name` as *critical* on `/login`: the password show/hide toggle at `Login.jsx:257` contains only an `MdVisibility` SVG and announces as "button".

It's systemic rather than isolated — `aria-label` appears 38 times across the whole codebase against a much larger population of icon-only buttons (close, refresh, filter, menu, avatar). The login toggle is just the one on a route axe could reach.

Related: `BottomTabBar.jsx:51` hardcodes `aria-label="Primary navigation"` in English, so the patient tab bar's landmark stays English in Filipino mode. The i18n linter doesn't inspect attributes.

**Fix**

Add `aria-label` to `Login.jsx:257` (toggling with `showPw`), then grep `<button` for children that are only an icon component and work through them.

Route the tab bar landmark through `t()` like every other string in that file.

---

### A11Y-4 · MEDIUM — The focus ring skips inputs, selects and textareas

**What I found**

`index.css:29` scopes the `:focus-visible` ring to `button`, `a` and `[role="button"]`. Form controls rely on the `.input` class carrying its own `focus:ring-2` — which works right up until a control doesn't use `.input`, and several don't.

Anything custom with a `tabindex` gets no ring at all. For keyboard-only users on the long intake forms, losing the caret position is the difference between a usable form and an unusable one.

**Fix**

Extend the base selector to `input`, `select`, `textarea`, `summary` and `[tabindex]:not([tabindex="-1"])`. It's an additive change — the existing `.input` ring stays and simply wins where it applies.

# Mobile & PWA — 4 findings

The PWA setup is unusually complete for a thesis project — maskable icons, rich-install screenshots, app shortcuts, a deliberate offline strategy that hands data caching to Firestore rather than fighting it at the worker. These are polish items on top of a sound base, with one real bug.

---

### MOB-1 · HIGH — Page content sits under the tab bar on notched iPhones

**What I found**

The bottom tab bar is `min-h-[60px]` plus `env(safe-area-inset-bottom)` — up to **94px** on an iPhone with a home indicator. The content area reserves a flat `pb-20`, which is **80px**, with no safe-area term.

*`Layout.jsx:1284` vs `BottomTabBar.jsx:49–50`*

So the last ~14px of every patient page is under the tab bar. In practice that's the bottom edge of the final Submit button on the request form and the intake wizard — the patient can see it, can't reliably tap it, and has nothing left to scroll.

The comment at `Layout.jsx:1282` says "56 px + safe-area", so the intent was right; the bar grew to 60px and the safe-area term never made it into the padding.

**Fix**

Replace the fixed `pb-20` with a computed value on the patient branch:

```jsx
style={{ paddingBottom:
  'calc(60px + env(safe-area-inset-bottom) + 1rem)' }}
```

Worth verifying on a real notched device rather than the simulator — this is exactly the class of bug that only shows up on hardware, and it's on the two screens a demo is most likely to walk through.

---

### MOB-2 · MEDIUM — The installed app's chrome is blue; the brand is teal

**What I found**

`theme_color` is `#3b82f6` — Tailwind's default blue-500 — in both `vite.config.js:26` and `index.html:12`. The actual brand is `brand-500` = `#0F6E56`, a deep teal.

On an installed Android PWA that colour drives the status bar tint and the splash screen. The app opens blue and resolves to teal. It's small, but it's the first frame of the installed experience and it's the one moment where the PWA reads as unfinished.

**Fix**

Set both to `#0F6E56`. Consider `background_color: '#FFFFFF'` too — the splash currently flashes `#f9fafb` before the white app shell paints.

---

### MOB-3 · MEDIUM — The mobile landing header is three stacked full-width buttons

**What I found**

`Landing.jsx:81` uses `flex-col gap-3 sm:flex-row` with `w-full sm:w-auto` buttons. Below 640px that stacks Install App / Register / Log In as three full-width blocks under a lone language toggle — roughly 250px of chrome before the hero starts.

The desktop header is a clean, well-composed single row. The mobile version reads as the responsive fallback rather than a designed state, and it's the first impression for the majority of the intended audience. The `h1` then wraps to five lines and pushes the primary CTA below the fold.

Two smaller things on the same page: the "Available Programs" grid shows loading skeletons with no timeout or error state, so a patient on a dead connection sees grey boxes indefinitely; and there are five differently-worded routes to the same registration flow ("Apply for Patient Account", "Register now", "Start with Step 1", "Apply Now", "Register as Patient").

**Fix**

Collapse the mobile header to one row: logo left, a single primary **Log In** right, everything else behind a menu — or drop the header CTAs entirely on mobile and let the hero's own CTA carry it.

Step the `h1` down at the small breakpoint so the CTA lands above the fold on a 390px viewport.

Give the programs grid a failure state after ~8s. Settle on two CTA labels: one primary verb for registration, one for sign-in.

### MOB-4 · LOW — PWA start URL and tab iconography

**What I found**

`start_url` is `/patient/request`. Every launch of the installed app opens the new-request form — including for a patient mid-way through tracking an existing request, and for any staff member who installs it (they bounce through `PrivateRoute` to their own dashboard).

Separately, the Request tab uses `MdFavorite` — a heart. In every other mobile app a heart means "favourite" or "like". For "submit a request for medical assistance" it's a false signal.

And `BottomTabBar.jsx:14` documents tabs that don't exist ("Dashboard, My Application, Documents, Messages, More") — the actual five are Dashboard, Status, Request, Messages, More.

**Fix**

`start_url: '/patient/dashboard'` — the dashboard already routes by role and gives returning patients their status at a glance. The Request shortcut in `shortcuts[]` already covers the direct path.

Swap `MdFavorite` for `MdPostAdd` or `MdAddCircleOutline`. Update the stale comment.

# Performance — 4 findings

Route-level code splitting is already done and done well — the per-role chunks are all under 75 kB. What's left is the entry chunk everyone downloads before any of that matters, which is the number that counts for a patient on a 3G connection in Cotabato.

---

### PERF-1 · HIGH — 1,457 kB entry chunk (388 kB gzipped) before anything renders

**What I found**

Production build, verified locally:

```
dist/assets/index-*.js   1,456.88 kB │ gzip: 387.93 kB
dist/assets/Application*    73.59 kB │ gzip:  19.13 kB
dist/assets/Requests-*      49.52 kB │ gzip:  13.34 kB
(!) Some chunks are larger than 500 kB after minification
```

The per-route splitting is genuinely effective — every lazy chunk is small. But `vite.config.js` sets no `build.rollupOptions.manualChunks`, so the Firebase SDK, React, the router, i18next, both locale files and every eagerly-imported page collapse into one 388 kB gzipped blob that must fully download and parse before first paint.

On a 3G connection that's roughly 8–12 seconds to interactive. CLAUDE.md names "patients on slow connections" as a design constraint, so this is the finding most directly at odds with the project's own stated goal.

**Fix**

Add `manualChunks` splitting `firebase/*` into its own vendor chunk and React + router into another. Firebase alone is the majority of the weight, and it caches independently of your app code across deploys.

Then reconsider what's eager. `PatientDashboard` and `Register` (877 lines) are both eagerly imported; a first-time visitor on `/` pays for both and needs neither.

Target under 150 kB gzipped for the entry chunk. It's reachable without touching application code.

---

### PERF-2 · MEDIUM — Both translation files ship to every user

**What I found**

`i18n/index.js` statically imports `en.json` (68 kB) and `fil.json` (76 kB) and hands both to `i18n.init()`. That's ~145 kB of raw JSON in the entry chunk, of which any given user reads half.

**Fix**

Load the saved language eagerly and the other via dynamic `import()` on `languageChanged`, using i18next's `addResourceBundle`. The toggle gains one network round-trip on first switch; every first paint gets ~70 kB lighter.

---

### PERF-3 · MEDIUM — The public landing page waits on Firebase Auth before it renders anything

**What I found**

`AuthContext.jsx:88` returns a full-page spinner while `loading` is true, and `AuthProvider` wraps the entire route tree in `App.jsx:93`. So `/`, `/login`, `/register` and `/install` — all fully public — block on Firebase Auth initialising and, for a returning user, a Firestore `getDoc` before painting a single pixel.

Stacked on PERF-1, a first-time visitor on a slow connection sees a blank page, then a spinner, then the hero. The gate is correct for protected routes; it's just applied one level too high.

**Fix**

Move the `loading` gate out of the provider and into `PrivateRoute`: render `children` unconditionally from `AuthProvider`, expose `loading` on the context, and have `PrivateRoute` show the spinner while it's true. Public routes then paint immediately.

`PrivateRoute` needs that check either way — right now it reads only `user`, and is correct purely because the provider happens to block above it. That's a load-bearing coincidence.

---

### PERF-4 · LOW — `react-pdf` is a dependency nothing imports

**What I found**

Zero imports of `react-pdf` or `pdfjs` anywhere in `src/`, `tests/` or `scripts/`. `DocViewerModal.jsx:165` renders PDFs with a plain `<object>`, which is the simpler and better call.

It's still in `dependencies`, still force-prebundled by `optimizeDeps.include: ['react-pdf']` (slowing dev server start), and `vite.config.js:97` still raises the workbox cache ceiling to 5 MB for "the PDF.js worker" that doesn't exist.

**Fix**

`npm uninstall react-pdf`, drop the `optimizeDeps` entry, and re-evaluate `maximumFileSizeToCacheInBytes` — a smaller ceiling keeps the 2.4 MB precache from growing quietly.

# Tooling & process — 3 findings

The quality gates that exist are well built. The gap is that one of them was scoped so narrowly it can't run over the codebase, and another can be switched off from inside the file it's guarding.

---

### PROC-1 · MEDIUM — There is no general lint, and the React Hooks rules are installed but disabled

**What I found**

`package.json` has `lint:i18n` and nothing else. `eslint.config.js` registers `eslint-plugin-react-hooks` in `plugins` but enables **zero** hooks rules — so `rules-of-hooks` and `exhaustive-deps` have never run.

There's also a config bug making a whole-repo lint impossible: `js.configs.recommended` applies globally, but `languageOptions.globals` is set only inside the narrow patient-files block. Linting `src/**` produces 47 `no-undef` errors for `console`, `document`, `fetch` and `URL` — noise that would bury any real signal, which is presumably why nobody runs it.

I ran ESLint with a corrected config. It found BUG-1 and BUG-2 immediately, plus 17 `exhaustive-deps` warnings and 71 unused variables (including nine dead imports in `Layout.jsx` alone). That's a real defect-per-minute rate from tooling already installed.

**Fix**

Add a second config block for `src/**/*.{js,jsx}` with `globals.browser`, `react-hooks/rules-of-hooks: 'error'` and `exhaustive-deps: 'warn'`. Add `"lint": "eslint src"` and put it in CI.

Fix the two `rules-of-hooks` errors first, then work the `exhaustive-deps` warnings down — each one is a potential stale-closure bug in a Firestore listener, which is the failure mode hardest to reproduce by hand.

---

### PROC-2 · MEDIUM — The i18n gate reports zero because one file switched it off

**What I found**

`npm run lint:i18n` is clean. But `IntakeWizard.jsx:1` carries a file-level `/* eslint-disable i18next/no-literal-string */`, so an entire patient-facing wizard is exempt.

The stated reason is sound — it uses the inline-bilingual pattern CLAUDE.md endorses (`"Step 1 of 5 · Hakbang 1 sa 5"`) and the linter can't recognise that as translated. The consequence is a UX inconsistency rather than a bug: **the language toggle does nothing on this screen.** Every other patient page swaps language; the intake wizard always shows both, in both modes.

Worth naming now because "bilingual, linter-enforced" is likely a thesis claim, and a panel member who toggles the language on the intake wizard will notice the difference.

**Fix**

Pick one and state it. Either move IntakeWizard onto `t()` like the rest of the patient surface, or document inline-bilingual as a deliberate exception for the wizard (defensible: a form being filled in with a social worker present benefits from both languages visible) and add a linter allow-pattern for `"English · Filipino"` so the exemption is scoped to that shape rather than the whole file.

---

### PROC-3 · LOW — Install requires `--legacy-peer-deps`, and nothing says so

**What I found**

A plain `npm ci` fails on this repo. `npm ci --legacy-peer-deps` succeeds — which is what `ci.yml` uses, so CI is fine. The flag is documented in a CI comment, but `README.md` and `DEPLOY.md` don't mention it.

Anyone cloning fresh — a panel member, your adviser, a teammate on a new machine — hits a wall of resolution errors on first contact with the project. Not a defect; just a bad first five minutes at exactly the wrong moment.

The underlying cause is an unresolved peer conflict in the Vite/Vitest tree (Vitest 4 against Vite 5). Worth resolving eventually, not before defense.

**Fix**

One line in the README's setup section. Optionally add `legacy-peer-deps=true` to a committed `.npmrc` so the plain command just works.

Also worth a quick pass on doc rot:

- CLAUDE.md still says i18n is "not yet integrated" and lists four roles where `constants.js` defines five.
- `vite.config.js:106` describes stripping "~200 console.log statements" that no longer exist (there are zero — all 204 remaining are `warn`/`error`, deliberately kept).
- `src/` contains a stray `{components,pages/...}` directory tree from a brace expansion that ran in PowerShell.

# What's genuinely strong

Audits skew negative by construction. For balance — and because several of these are things a panel should be told about rather than left to discover — here is what stood out as above the bar for a capstone project.

**The Firestore rules are serious work.** 53 kB of rules with per-collection reasoning, split read statements for debuggability, `diff().affectedKeys().hasOnly()` field pinning, and inline notes recording which production incident drove each hotfix. Most teams ship `allow read, write: if request.auth != null`. SEC-1 and SEC-3 are gaps in an otherwise well-argued model.

**Transactional integrity in registration.** The access-code claim re-reads status inside the transaction, writes user + code + private sub-doc atomically, and rolls back the orphan Auth account on failure. The race condition it guards is one most projects don't notice until it bites.

**142 passing tests across four suites.** Utils, components, Cloud Functions and rules, wired into GitHub Actions with the emulator job running in parallel. All three suites I could execute passed clean. The handoff doc's own caveat — that these are smoke and unit tests, not end-to-end — is the right framing to bring to a panel.

# Questions a panel could ask

Three of the findings above map onto questions that are natural to ask about this architecture. Better to have the answer ready than to meet it cold.

> **"You rate-limit the access code check. What stops someone from just reading the database directly?"**

Today: nothing (SEC-1). After the fix, the honest answer is strong — the code is a claim gate issued in person by Medical Social Services, the client cannot read the collection at all, and the only path to a yes/no answer is a callable function throttled per-account and per-network. Fix it first, then this question becomes one you want asked.

> **"Is this accessible? Who checked?"**

Currently the answer is "not verified", and axe disagrees on all four public routes. A11Y-1 and A11Y-2 are both close to single-file fixes. Do them and you can say: "WCAG 2.1 AA, verified with axe-core across the patient flow" — and show the run. That is a much better position than conceding it as future work.

> **"You have 142 tests. What do they actually prove?"**

Answer the way `handoff-2026-06-29.md` already does: smoke, unit and rules-predicate coverage, not end-to-end. Then use SEC-1 as the illustration — a rules test asserted the enumeration hole as correct behaviour. Naming a limitation you found yourself, before the panel finds it, reads as engineering maturity rather than a gap.
